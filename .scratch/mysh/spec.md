# mysh — git-backed home-folder manager

Status: ready-for-agent

## Problem Statement

Setting up dotfiles, packages, environment/session config, and secrets on a new or temporary device is currently either manual and error-prone, or requires stitching together several tools (a dotfile manager, a secrets tool, a package manager) that don't share a consistent mental model. None of the existing options combine: git as the actual storage/remote mechanism, directly editable config (not a read-only rendered output), whole-folder tracking (new files show up automatically, not just files you remembered to register), a clean way to mix plaintext and secret fragments into one target file, and a package-management layer that can be **fully and cleanly uninstalled**, returning a machine to exactly the state it was in before the tool ever touched it — all while keeping the dependency footprint low enough to bootstrap on almost any Linux or macOS device with one command.

## Solution

`mysh`: a single statically-compiled Rust CLI binary that treats a user's public git repository as the single source of truth (`Source`) for their home folder. It renders `Source` into real files on disk (`Target`, mirrored path-for-path under `$HOME`) through one uniform render step (`Apply`), manages CLI-tool packages via `mise` (self-bootstrapped on first need), transparently decrypts passphrase-encrypted secrets, composes multi-fragment config files, and tracks everything it does on a given device in an `Application Log` so that a single `Teardown` command can reverse all of it — dotfiles, packages, `mise` itself, and the bootstrap installer — back to a pristine, first-touch state. The only pre-existing dependency assumed on a device is `git`; everything else, including the `mysh` binary itself, is fetched by a one-line install script hosted inside the user's own repo.

Full domain vocabulary is defined in `CONTEXT.md`; the decisions with lasting consequences are recorded in `docs/adr/0001` through `0005`. Both already exist in this repo and are authoritative background for implementation.

## User Stories

1. As a user setting up a brand-new device, I want to run a single one-line command that installs `mysh` and applies my entire home-folder configuration, so that I don't have to remember or type more than one address (my own repo's location).
2. As a user, I want that one-line install script to be hosted inside my own public repo, so that the address I remember for bootstrapping is the same address I already use for my dotfiles.
3. As a user on a device where `git` isn't guaranteed to be anything but present, I want `mysh` to have no other required pre-existing dependency, so that I can bootstrap it on almost any Linux or macOS box, including a throwaway/temporary one.
4. As a user, I want `mysh` to detect and fetch the correct prebuilt binary for my OS/architecture during bootstrap, so that I never have to build it myself on a new device.
5. As a user, I want my dotfiles repo (`Source`) to mirror my home directory path-for-path, so that I can predict where any given file in the repo will end up without a separate mapping file.
6. As a user, I want to edit a plain config file either directly on disk (`Target`) or in the repo (`Source`), so that neither location is read-only.
7. As a user, I want every file type (plain config, secret, fragment-composed) to go through the same render (`Apply`) mechanism, so that diffing and reasoning about drift works identically regardless of file type.
8. As a user, I want to see a three-way comparison — what's live on disk (`Target`), what's committed locally (`Source`), and what's on the remote (`Remote`) — so that I always know exactly what would change before I act.
9. As a user, I want a `save` operation that captures my live edits back into the repo, commits, and pushes, so that changes I make directly on a device propagate back to my source of truth.
10. As a user, I want `save` to show me a diff and require explicit confirmation before it commits/pushes anything, so that I never lose track of what just changed.
11. As a user, I want a `reset` operation that discards any local drift and forces my device back to exactly what's on the remote, so that I can get a clean, known-good state on demand.
12. As a user, I want `reset` to show me a diff and require explicit confirmation before it overwrites anything, so that I never silently lose local edits I cared about.
13. As a user, I do not want `mysh` to attempt automatic three-way merges between two devices' changes, so that conflict resolution stays predictable (I explicitly choose local-wins via `save` or remote-wins via `reset`, and drop into real `git` myself for anything more complex).
14. As a user, I want to track an entire directory (not just individual files I remember to add), so that a new file that shows up later (e.g. a new plugin config) is automatically picked up as a candidate to save, instead of silently staying unmanaged.
15. As a user, I want directory-level tracking to be something I opt into per-directory, so that most files stay in simple, predictable file-mode tracking unless I explicitly ask for a directory to be watched as a whole.
16. As a user, I want a directory I've opted into tracking to let me exclude noisy, generated files (caches, lockfiles, swap files) from ever showing up as "new," so that directory-mode tracking doesn't flood my diffs with junk I never intended to manage.
17. As a user, I want to mark specific files as secrets (distinguishable at a glance, e.g. by a file extension), so that I can tell which parts of my repo are encrypted without opening them.
18. As a user, I want all my secrets protected by a single passphrase I remember, rather than a keypair I'd have to transport securely to every new device, so that unlocking my secrets on a brand-new or temporary device never requires a separate secure-channel step.
19. As a user, I want to be prompted for my passphrase only when a command actually needs to decrypt something, so that commands that don't touch secrets never bother me for it.
20. As a user, I do not want my passphrase or derived key cached anywhere (memory-resident agent, OS keychain, disk), so that there's no residency window where my decryption key could be exfiltrated after I've finished a command.
21. As a user, I want to diff a secret by comparing its freshly-decrypted committed value against its live decrypted value on disk, so that I never compare ciphertext to plaintext and never get a meaningless diff.
22. As a user, I want decrypted secret files to be written with restrictive file permissions automatically, so that a decrypted SSH key or credential isn't left world-readable on disk.
23. As a user, I want to build a single config file out of multiple fragments (e.g. a base fragment, a work-specific fragment, a secret fragment), so that I can compose configuration from reusable, independently-editable pieces.
24. As a user, I want one of those fragments to be encrypted while the others stay plaintext, so that I can mix secret and non-secret content in a single rendered file without encrypting the whole thing.
25. As a user, I want new fragments dropped into a fragment directory to be automatically picked up by the renderer without any registration step, so that adding a new piece of a composed file is as simple as adding a file.
26. As a user, I understand that a fragment-composed file is derived-only — if I hand-edit the live merged file directly, I want `mysh` to show me that drift on diff, but only let me discard it via `reset`, not "save" it back (since there's no unambiguous fragment to attribute the edit to), so that I'm never surprised by an automatic, ambiguous write into the wrong fragment.
27. As a user setting up a device that already has some of the files `mysh` wants to manage, I want the pre-existing file backed up automatically before being overwritten, so that a first-time apply never silently destroys something that predates `mysh`.
28. As a user, I want `mysh` to remember whether a given target file was newly created versus overwritten-with-backup, so that `teardown` can correctly delete the former and restore the original content of the latter.
29. As a user, I want to declare CLI tools/binaries I want installed, using whatever backend `mise` already supports (GitHub releases, npm, pip, cargo, etc.), so that I don't need `mysh` to reinvent package resolution.
30. As a user, I want to mark some packages as "eager" (installed immediately during apply) and others as "lazy" (installed only the first time I actually run them), so that a fresh device doesn't have to pay the install cost for tools I might not use on that device.
31. As a user, I want to just type a lazy tool's normal command name (not a special prefixed command) and have it transparently install itself on first use, so that lazy tools feel exactly like already-installed tools.
32. As a user, I want to be able to declare a lazy package whose install specifier differs from its actual binary name, so that tools like GitHub-release binaries with non-obvious binary names still get the right shim.
33. As a user, I want `mysh` to install `mise` itself automatically if it isn't already present, so that I don't have to separately remember to bootstrap my package manager.
34. As a user, I want `mysh`'s package management explicitly scoped to CLI tools/binaries (not system libraries, GUI apps, or compilers), so that the promise of a fully clean uninstall stays achievable rather than best-effort.
35. As a user, I want a single `teardown` command that reverses everything `mysh` has done on a device — every file it created or overwrote, every package it installed, `mise` itself if `mysh` installed it, every PATH/shell-rc line it added, and the bootstrap installer's own footprint — so that I can return a borrowed, temporary, or work device to exactly its pre-`mysh` state.
36. As a user, I want every device's home-folder configuration to be uniform (no per-machine profile variation) in this version, so that I don't have to reason about which subset of config applies where.
37. As a user, I want my dotfiles repo to be public, with security relying entirely on per-file passphrase encryption (not repo-level access control), so that cloning it on a brand-new device never requires me to first solve a git-credential bootstrapping problem.

## Implementation Decisions

- **Distribution & language**: `mysh` is a single statically-compiled Rust binary, built per OS/architecture. It shells out to the real `git` binary for all VCS operations and to `mise` for package operations — both discovered via `PATH`, no vendored/embedded implementations of either.
- **Dependency floor**: `git` is the only pre-existing dependency assumed on a target device. `mise` is not assumed present — `mysh` bootstraps it on first need and records that bootstrap in the `Application Log`.
- **Repo layout**: `Source` mirrors `$HOME` path-for-path, and lives at `profile/` inside `mysh`'s own repo (not a separate repo) — a bootstrap sparse-checkout fetches only `profile/`, never the Rust tool source. No manifest/config file maps paths — the filesystem layout of `Source` *is* the configuration, per a pure naming convention:
  - A plain file `foo` in `Source` → renders to `foo` at the same relative path under `Target`.
  - A file ending in `.age`, e.g. `foo.age` → treated as a `Secret`; `Apply`/`Diff` decrypt it in memory and the rendered `Target` path has the `.age` suffix stripped.
  - A directory named `foo.d/` → treated as a `Fragment`-composed target; its contents render, in lexical filename order, into a single `Target` file named `foo` (any `.age`-suffixed fragment inside is decrypted before concatenation).
  - A directory containing a `.track` marker file at its root → opts that directory into `Directory-mode tracking` (see below); its absence means `File-mode tracking` (only files explicitly present in `Source` are managed; sibling files in the same `Target` directory are never scanned or flagged).
- **Render pipeline (`Apply`)**: uniform across all three file kinds (identity copy / decrypt / concatenate-fragments) — no symlinks are used anywhere (see ADR-0002), so `Target` is always a real, independently editable file.
- **Three-state model**: `Source` (repo working tree), `Target` (rendered files on disk), `Remote` (git remote). The `diff`/`status` surface reports drift across all three simultaneously.
- **`save`**: captures `Target` drift into `Source`, commits, pushes to `Remote`. Local wins. Always shows the resulting diff and requires explicit confirmation before executing. Not available for `Fragment`-composed targets — those only support `diff` (to observe drift) and `reset` (to discard it); there is no automatic attribution of a merged-file edit back to a specific fragment.
- **`reset`**: discards local drift in both `Source` and `Target`, force-fetches `Remote`, re-applies. Remote wins. Always shows the resulting diff and requires explicit confirmation before executing. No three-way merge is attempted anywhere in `mysh`; a user who needs a real merge drops into `git` directly against `Source`.
- **`add <path>`**: starts tracking a new path in `Source` — dispatches on whether `<path>` exists on disk relative to `Target`: a file → copies its content into `Source` at the mirrored path (or, with `--secret`, encrypts it there instead); a directory → creates a `.track`-marked mirrored directory (optionally seeded with repeatable `--ignore <pattern>` flags), shows the matched file list, and bulk-copies it into `Source` only after explicit confirmation; a path that doesn't exist at all → treated as a package specifier, `lazy` by default. A lazy add writes a real, portable shim file into `Source` at `.mysh/bin/<bin_name>` (`--bin <name>` overrides the default derived from the specifier). An eager add (`--eager`) declares the specifier in `Source`'s `config.toml` via `mise config set`, requiring an already-resolvable `mise` (system-wide, or previously bootstrapped by an earlier `apply`) — `add` never bootstraps one itself, since that would touch `Target`; `--bin` has no effect with `--eager`, since `mise` resolves the binary name itself. Every variant refuses, pointing at `save` (files/directories) or at the existing shim file/`config.toml` entry (packages), when the target is already tracked/declared. `add` only ever touches `Source`, never `Target`, and never commits or pushes.
- **Directory-mode tracking**: on `diff`, any directory marked with `.track` is recursively walked on the live `Target` side (plain filesystem walk, independent of git) and compared against `Source`'s contents for that directory. Files present in `Target` but absent from `Source` are flagged **new** (a `save` candidate); files present in `Source` but absent from `Target` are flagged **missing** (a `reset` candidate). The `.track` file's own content is a newline-separated list of glob patterns to exclude from this scan; an empty `.track` file tracks everything under that directory.
- **Secrets**: a single, shared `Passphrase` (not a keypair — see ADR-0003) is used everywhere. The encryption key is derived from the `Passphrase` via Argon2id; content is encrypted with an AEAD cipher (XChaCha20-Poly1305), using an established, audited crate rather than a hand-rolled scheme. Diffing a `Secret` always decrypts a fresh copy of `Source`'s ciphertext and compares plaintext-to-plaintext against `Target` — never ciphertext-to-plaintext. The `Passphrase` is requested interactively, fresh, on any command that needs to decrypt something, and is never cached, stored, or handed to an OS keychain or background agent. Any file written as the result of decrypting a `Secret` gets restrictive file permissions applied automatically (no world/group readability).
- **Pre-existing file handling**: on first `Apply` to a device, if the `Target` path already has content, that content is backed up (and recorded in the `Application Log` as "pre-existing, overwritten") before being replaced. Files with no prior content at that path are recorded as "created fresh." This distinction is what lets `teardown` restore versus delete correctly.
- **Packages**: a "package" means a CLI tool/binary installed into an isolated, `mysh`-owned prefix via `mise` — explicitly not a full system package (library, GUI app, compiler); see ADR-0005. Eager and lazy packages are declared through two entirely different mechanisms now (ADR-0006), not a shared declarations file:
  - **Eager** packages are entries in mise's own native `[tools]` table in `config.toml` (an ordinary tracked dotfile, rendered like any other). `Apply` installs every declared eager package in one blanket `mise install` call, and each becomes reachable on `PATH` through mise's own shim/activation mechanism (`.mysh/mise/shims`, which `bootstrap.sh` adds to `PATH` alongside `.mysh/bin`) — not a mysh-generated shim.
  - **Lazy** packages are real, portable shim script files checked into `Source` at the mirrored path `.mysh/bin/<bin_name>`, identity-copied into `Target` by `Apply` like any other tracked file. A lazy shim resolves `$HOME` and `mise` at *run time*, not at write time, so the identical file is correct on every device it's rendered to; invoking the plain command name runs the shim, which calls `mise x <specifier> -- <bin_name> "$@"`, installing on first real invocation.
- **`Application Log`**: a per-device record of every file `mysh` created versus overwrote-with-backup, every package it installed, every `PATH`/shell-rc line it added, and the bootstrap installer's own footprint (binary location, install-time `PATH` additions). This is the sole input to `teardown`.
- **`teardown`**: replays the `Application Log` in reverse — deletes created files, restores backed-up originals, uninstalls packages via `mise`, removes `mise` itself if `mysh` installed it, strips any `PATH`/rc-file lines it added, and removes the `mysh` binary and installer footprint. Net effect: the device returns to its state from before the bootstrap one-liner was ever run.
- **Bootstrap**: a `bootstrap.sh` script lives at the root of `mysh`'s own (public) repo, alongside the Rust tool source and the `profile/` `Source` directory. The one-line install is `curl -fsSL <raw-content-url-of-that-repo>/bootstrap.sh | sh`. The script detects OS/architecture, downloads the matching prebuilt `mysh` binary from `mysh`'s own GitHub Releases, places it on `PATH` (recording this in the `Application Log`), sparse-checks-out only the `profile/` directory of the same repo it was fetched from as `Source` (skipping the Rust tool source entirely), then hands off to the binary to bootstrap `mise` and run the initial `Apply`.
- **Trust model**: the repo — Rust tool source and `profile/` `Source` together — is public (ADR-0004). Only `.age`-suffixed file *content* is protected; repo structure, plain config content, machine/package names, and directory layout must be treated as world-readable at all times, including everything under `profile/`. This is a hard boundary for anything built on top of `mysh`, not merely a default.
- **No per-device/profile variation** in this version — every device that applies a given `Source` gets identical config. (Deferred; see Out of Scope.)
- **Testing seam**: the CLI's root command accepts three injectable locations — `SOURCE_DIR`, `TARGET_DIR` (stands in for `$HOME`), and `REMOTE_URL` — plus a non-interactively suppliable `Passphrase`. These are real, user-facing configuration points, not test-only scaffolding. `git` and `mise` are invoked as subprocesses discovered via `PATH`.

## Testing Decisions

- A good test in this codebase drives the real CLI entrypoint against injected `SOURCE_DIR`/`TARGET_DIR`/`REMOTE_URL` (a local bare repo via `file://`) and a fixed test `Passphrase`, and asserts on externally observable outcomes — files on disk, command output/exit codes, commits in the test repos — never on internal function calls or module structure.
- Use the **real** `git` binary in every test; it's fast, deterministic, and local, so mocking it would only remove confidence for no speed benefit.
- Stub `mise` via a `PATH` override for any test involving packages, to avoid real network installs during test runs; assert against the `mise` config and shim scripts `mysh` generates/invokes, not against actually-installed software.
- There is no prior art in this repo yet — this is the first feature, and the CLI-entrypoint seam described above should be treated as the pattern future test suites in this codebase follow.
- Modules/behaviors to cover: the `Apply` render pipeline for all three file kinds (plain/secret/fragment); `diff` in both file-mode and directory-mode (including `.track` ignore patterns); `save` (including its refusal on fragment-composed targets); `reset`; pre-existing-file backup-and-overwrite on first apply; `Application Log` accuracy (created-vs-overwritten, packages, PATH/rc lines) and `teardown`'s correctness against it; `add`'s two package-declaration paths (real lazy shim file, `mise config set` for eager); `Apply`'s blanket eager install and lazy-shim identity-copy; and the bootstrap script's logic to the extent it can be exercised without actually curling and executing it against a real machine.

## Out of Scope

- Per-device/profile variation (every device gets uniform config in this version).
- Automatic three-way merge or any conflict resolution beyond `save` (local-wins) and `reset` (remote-wins); real merges are done by dropping into `git` directly.
- Full system package management — libraries, GUI applications, compilers, or anything installed via `apt`/`dnf`/`pacman`/`brew`. "Package" means a `mise`-managed CLI tool/binary only.
- OS keychain integration, passphrase caching, or any background agent/daemon for secrets.
- Private-repo support and the git-credential-bootstrapping problem that comes with it (the repo is public by design — ADR-0004).
- Per-recipient secret revocation (a consequence of the single-shared-passphrase model — ADR-0003).
