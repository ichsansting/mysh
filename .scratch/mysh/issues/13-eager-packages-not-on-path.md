# 13 — Eager packages install but never land on `PATH`

**What to build:** `package::apply` (`src/package.rs:81-104`) installs every eager package via `mise install`, but nothing afterward puts the installed binary anywhere a plain command-name lookup would find it. Only lazy packages get a shim written into `mise::bin_dir` (`<target>/.mysh/bin`), which `bootstrap.sh` adds to `PATH`. `mise install` alone does not add anything to `PATH`: mise normally exposes installed tools either via its own shims directory (`$MISE_DATA_DIR/shims`) or via `mise activate` in the shell, and mysh does neither — it points `MISE_DATA_DIR` at its own isolated `target/.mysh/mise` and never adds `target/.mysh/mise/shims` (or equivalent) to `PATH` anywhere, not in `package.rs` and not in `bootstrap.sh`.

**Net effect today:** declaring a package `eager` downloads it during `apply` but the plain command name resolves to "command not found" afterward — only `lazy` actually works end-to-end for a user typing the tool's name.

**Blocked by:** 08 — Packages: eager install via mise, 09 — Packages: lazy install via shims

- [x] Added `eager_package_shim_is_generated_and_reachable_on_the_bootstrap_path` and `both_eager_and_lazy_packages_get_a_shim_after_apply` in `tests/package_integration.rs`, asserting the eager package's shim actually runs via `Command`, not just that `mise install` was called.

## Agent Brief

**Category:** bug
**Summary:** Eager packages install during apply but never become reachable on `PATH` under their plain binary name — only lazy packages actually work end-to-end today.

**Current behavior:**
Package application splits declared packages into two paths: eager packages are installed immediately via the package manager's install command, and lazy packages instead get a generated shim written into the PATH-resident bin directory that installs-on-first-use and execs the tool. Only the lazy path produces anything reachable on `PATH`. After an eager package installs, its plain binary name resolves to "command not found" — the install step alone doesn't expose it anywhere `PATH` lookups would find it, and the package manager's own built-in shim/activation mechanism (verified live) doesn't work either, since it depends on a config file mysh doesn't write.

**Desired behavior:**
Every declared package — eager or lazy — is reachable under its plain binary name after `apply`, via the same shim mechanism the lazy path already uses (a shim that invokes the package manager with the tool's install specifier and binary name explicit, not dependent on any external config-file-based activation). Eager packages keep installing during `apply` itself (unchanged) — so their shim's first real invocation is instant, no install delay — while lazy packages keep deferring the install cost to first invocation. The only remaining difference between the two classifications is *when* the install happens, not whether the tool ends up on `PATH`.

**Key interfaces:**
- The package-application entrypoint currently branches into two independent steps keyed on the eager/lazy flag: an install step (eager-only) and a shim-generation step (lazy-only). The shim-generation step should run for every declared package regardless of classification; the install step stays scoped to eager packages only.
- The shim-generation helper itself needs no behavioral change — it already takes a specifier and binary name and produces a self-contained script; it just needs to be invoked for eager packages too.

**Acceptance criteria:**
- [x] After `apply`, an eager package's binary name is actually executable via the same `PATH` state the lazy path establishes — assert by invoking the resolved binary, not just asserting the install command was called
- [x] Lazy packages continue to defer installation to first invocation, unchanged
- [x] Eager packages still install during `apply` itself, not deferred
- [x] A package declared eager and a package declared lazy both end up with a generated shim after `apply`

**Out of scope:**
- Adding any new `PATH` management to the bootstrap installer — the bin directory both classifications shim into is already on `PATH`
- Teaching mysh to write the package manager's own config file format to make its built-in shim/activation mechanism work — confirmed unnecessary, more moving parts than reusing the existing shim
- Changing package declaration syntax or the eager/lazy classification semantics themselves
- Teardown changes — the existing final sweep of mysh's owned state directory already removes shims for both classifications
