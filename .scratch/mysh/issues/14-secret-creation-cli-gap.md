# 14 — No CLI path to add a new file, folder, package, or secret

**What to build:** There is no supported way to start tracking something new without hand-editing `Source` directly. `apply`/`diff`/`save`/`reset` all *consume* paths that are already tracked; nothing lets a user turn an untracked `Target` file into a new tracked file in `Source`, mark a new directory for directory-mode tracking, declare a new package, or turn a plaintext file into an encrypted `Secret`. Today all four require reaching for `git`/a text editor directly, or (for secrets) a throwaway Rust snippet calling `secret::encrypt`.

This ticket originally covered only the secret-creation gap; grilling on 2026-08-02 broadened it to a single `add` verb covering all four onboarding gaps, since they're the same underlying problem (no CLI path to start tracking something new).

## Agent Brief

**Category:** enhancement
**Summary:** Add a unified `mysh add <path>` command that starts tracking a new file, directory, or package in `Source` — including an `--secret` mode that encrypts instead of copying plain.

**Current behavior:**
`apply`, `diff`, `save`, `reset`, and `teardown` all operate on paths already known to `Source` (tracked files, `.track`-marked directories, declared packages). Getting a *new* path under management requires manually placing a file in `Source` at the right mirrored path, manually creating a `.track` marker, manually appending a line to `.packages`, or (for secrets) writing a throwaway program that calls `secret::encrypt` directly. None of this goes through the CLI.

**Desired behavior:**
A single `mysh add <path> [--secret] [--eager|--lazy] [--bin <name>] [--ignore <pattern>]...` command dispatches based on what `<path>` resolves to on disk (relative to the resolved `target_dir`, accepting an absolute or `~`-expanded argument):

- **Doesn't exist on disk at all** → treat `<path>` as a `mise` package specifier (package-add).
- **Exists as a file** → file-add.
- **Exists as a directory** → folder-add.

*File-add*: copies the file's current `Target` content into `Source` at the mirrored relative path, so the path becomes tracked going forward. Fails with a clear error if that relative path is already tracked in `Source` — the message should point the user at `save` instead, since `add` is exclusively for previously-untracked paths. With `--secret`, encrypts the content through the same passphrase machinery every other secret-touching command already uses and writes the `.age`-suffixed path instead of a plain copy. No confirmation prompt — the user named one explicit path. `--secret` combined with a directory or package argument is an error.

*Folder-add*: creates the mirrored directory in `Source` and marks it for directory-mode tracking (the same marker mechanism issue 05 already implements — a directory with that marker present is recursively walked and diffed against `Source` on every `diff`/`save`, independent of git). Fails with a clear error if that directory is already so marked, pointing at `save`. Any `--ignore <pattern>` flags (repeatable) are written into the new marker file using its existing pattern syntax (newline-separated globs; slash-containing patterns match a full path, bare patterns match any path component) before the walk happens, so excluded paths never even appear in what gets shown next. The command then walks the directory respecting those patterns, prints the list of files it's about to copy, and requires an explicit `y/N` confirmation (declining leaves `Source` untouched) before copying every matched file into `Source` at their mirrored paths.

*Package-add*: appends one line to the package declarations file using its existing tab-separated format (specifier, classification, optional bin name). Fails with a clear error if that exact specifier is already declared, pointing the user at editing the declarations file directly rather than silently deduplicating or overwriting. Classification defaults to lazy (not eager) when neither `--eager` nor `--lazy` is passed — eager packages currently have a known bug (installed but unreachable on `PATH`, tracked separately) so lazy is the classification that actually works end-to-end today. `--bin <name>` overrides the default derived binary name, same override semantics the declarations format already supports. This command does not attempt to discover or enumerate multiple binaries a specifier might provide — it writes exactly one declaration line per invocation. A specifier whose install produces more than one binary a user wants shimmed still requires adding further lines by hand, same as before this ticket.

**Key interfaces:**
- Whatever function resolves a `PassphraseFn`-style closure for encrypting on demand — file-add's `--secret` path should reuse it exactly as `apply`/`save`/`reset` already do, not build a second passphrase-prompt path
- The directory-tracking marker file's existing pattern-matching logic (parsing newline-separated glob patterns, matching a path against them) — folder-add's `--ignore` handling should reuse it rather than reimplementing glob matching
- The package declarations file's existing line format and default-bin-name derivation — package-add should reuse both rather than introducing a second way to express a package declaration
- `Config::resolve`-style source/target directory resolution — `add` needs both, same as every other subcommand

**Acceptance criteria:**
- [x] `mysh add <path>` for an untracked file that exists on `Target` copies its content into `Source` at the mirrored path; a subsequent `apply`/`diff` shows it as tracked with no drift
- [x] `mysh add <path>` for an already-tracked file errors without modifying `Source`, and the error text references `save`
- [x] `mysh add <path> --secret` writes an `.age`-suffixed file in `Source` whose content round-trips through the existing decrypt function back to the original plaintext
- [x] `mysh add <path> --secret` where `<path>` is a directory, or where the argument resolves to a package specifier, errors without writing anything
- [x] `mysh add <folder-path>` for an untracked, existing directory creates the directory-tracking marker in `Source`, then shows a confirmation prompt; declining leaves `Source` completely unchanged; accepting copies every non-ignored file under that directory into `Source` at their mirrored paths
- [x] `mysh add <folder-path> --ignore <pattern>` excludes matching files from both the shown list and the copy, using the same pattern semantics as the existing directory-tracking marker file
- [x] `mysh add <folder-path>` for an already-tracked directory errors without modifying `Source`, and the error text references `save`
- [x] `mysh add <specifier>` for a path that doesn't exist on disk appends one correctly-formatted line to the package declarations file with `lazy` classification by default
- [x] `mysh add <specifier> --eager` / `--lazy` / `--bin <name>` override classification/bin name as expected in the appended line
- [x] `mysh add <specifier>` for a specifier already present in the package declarations file errors without modifying the file
- [x] Every new behavior is covered by tests driving the real CLI entrypoint against injected `SOURCE_DIR`/`TARGET_DIR`/`Passphrase`, per this repo's established testing pattern
- [x] `spec.md`'s command list is updated to include `add`

**Out of scope:**
- Fixing issue 13 (eager packages not landing on `PATH`) — `add` only needs to default to the classification that already works
- Auto-discovering every binary a package specifier provides
- Any confirmation prompt for single-file add (only the folder bulk-copy path requires one)
- Changing `save`'s, `diff`'s, or `.track`'s existing behavior for already-tracked paths
- A default/built-in ignore list for folder-add (e.g. auto-excluding `.git`, `node_modules`) — only user-supplied `--ignore` patterns
